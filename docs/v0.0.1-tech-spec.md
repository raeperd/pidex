# Pidex v0.0.1: Desktop Pi workflow

Implementation target, not implemented.

## Problem statement

Pidex needs a usable Pi desktop client with clear module ownership and reproducible use-case tests. The repository currently contains only a skeleton.

## Solution

Launch Electron on macOS, choose one project, and use one Pi conversation. Show streamed Markdown, collapsible tool inputs/results, model name, and status. Pi owns history; closing the window keeps work running.

## User stories and acceptance scenarios

Each row pairs one user story with one acceptance scenario. Use the same UC ID in its test name; edge-case variants stay under that ID.

| ID    | User story                                                                                                | Acceptance scenario                                                                                                                                           |
| ----- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Implementation decisions

The application has three main processes: Electron main, the Svelte renderer, and one backend child. The Pi SDK runs inside the backend child. API definitions are shared code, not a process. Electron and Pi tools may also create supporting subprocesses.

| Module  | Runs in           | Owns                                                                                                               |
| ------- | ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| Desktop | Electron main     | Windows, folder picker, backend child lifetime, connection credentials, current session locator                    |
| API     | Shared code       | Browser-safe Effect Schema and Effect RPC definitions                                                              |
| Backend | Backend child     | Embedded Pi SDK, session persistence, run lifetime, prompt acceptance, cancellation, events, snapshots and cleanup |
| Web     | Electron renderer | Rendering, drafts and connection status                                                                            |

- **Transport:** Electron owns a loopback HTTP/WebSocket backend child. Use Effect RPC + Schema, Effect backend logic, and ordinary Svelte UI code. Web imports shared API definitions, never backend code. Require a per-launch credential and approved origins; preload exposes narrow native capabilities. Keep composition at process entry points.
- **Pi:** Pin the latest stable SDK at implementation. Reuse credentials, default model resolution, stock tools, retry, compaction, and project instructions. Disable external extensions, skills, templates, themes, custom system prompts, and package resource loading without modifying user configuration.
- **History:** Pi JSONL files are authoritative; no pidex database. Electron retains the exact session locator for backend recovery. Unfinished output may be absent; the first turn may have no saved file. Cancellation does not undo file changes.
- **API:** Send atomically accepts nonempty input while idle. Stop targets a run and waits for cancellation. Watch sends a snapshot then ordered updates without a gap. Backend-owned runs survive client disconnects. Never automatically resend prompts; reconnect reconciles state and exposes uncertain acceptance.
- **State:** Idle → running → stopping/idle. Failures return to idle with an actionable typed error. Busy/disconnected UI keeps drafts editable but disables Send; the backend independently rejects busy submissions. Credentials never reach the renderer or logs. Keep the project fixed until app exit.

## Testing decisions

### Coverage

- Use Playwright Electron on macOS. Support is experimental; pin compatible versions.
- If Playwright Electron lacks a required testing capability, consider WebdriverIO with `@wdio/electron-service`.
- Run UC-01–11 and UC-13 through the Electron UI and lifecycle.
- Run UC-12 against the full app using an unauthorized client.
- Keep supporting integration checks under the same UC ID; they supplement application scenarios.
- Assert visible results, saved files, and process lifetime.

### Test setup and debugging

- Run the real Electron app, preload, backend, transport, and Pi SDK.
- Control only model responses, native dialog results, and network/process failures. Keep application handlers and UI state real.
- Supply native dialog results before invocation; automate window close, activation, Quit, and child termination.
- Use temporary projects, sessions, and credentials. Synchronize explicitly and clean up processes/files.
- Give each scenario starting conditions, actions, expected results, and an exact rerun command.
- Provide launch, per-UC rerun, and visible step-through commands, fixture setup, and artifact locations.
- Save traces, screenshots, and redacted logs on failure. Bug reports include UC ID, versions, steps, and expected/actual results.

### Release checks

- Pass all 13 automated scenarios, lint, formatting, types, and build in macOS CI.
- Manually check native dialogs and Dock behavior; these checks supplement automation.
- Record a real-Pi run in a disposable project: create/read a file, Stop, and reopen the window.
- Keep paid requests out of CI. Remove the empty-test exemption when tests exist.

## Implementation workflow

1. Choose a use case; add shared setup only as needed.
2. Write its application test and observe the expected failure.
3. Implement the smallest change that passes.
4. Refactor with tests green.
5. Watch the Electron scenario and record verification results.

- Each PR names its UC IDs and verification results.
- Related cases may share a PR; there is no fixed PR count.
- Bug fixes add regression coverage under the owning UC ID.
- Release v0.0.1 when every release check passes.

## Out of scope

- Installers/signing, Windows/Linux desktop acceptance, and remote access.
- History/project lists, project switching, last-session restore after full app exit, multiple sessions, automatic backend restart, and independent daemons.
- Model/thinking controls, login UI, external customization, steering/queues, dedicated thinking/token/compaction displays.
