# Pidex v0.0.1: Desktop Pi workflow

Status: agreed implementation target, not implemented. This document defines the
first working desktop development version after the project reset. It takes
precedence over the older [v1 product reference](prd.md) for this milestone.

## Outcome and scope

On macOS, launch Electron from a development command, choose a project folder,
and work in one Pi conversation. Send prompts, follow assistant text and tool
activity, stop a run, and return to ongoing work after closing the window.

Keep the implementation small enough that each use case has one clear owner and
a repeatable test. Prefer a few modules with small interfaces over forwarding
layers, generic provider abstractions, or a second copy of Pi's state.

Included:

- A native folder picker. The selected project stays fixed for the app lifetime.
- One active Pi session and one accepted prompt at a time.
- Assistant Markdown, collapsible tool inputs/results, model name, and status.
- Pi's built-in coding tools and normal session-file persistence.
- Closing/reopening the window without interrupting Pi.
- Manual backend restart that reopens the current saved Pi session.

Deferred:

- Installers, signing, notarization, and Windows/Linux desktop acceptance.
- Session lists, history pickers, project registries, and project switching.
- Remembering the last project/session after the whole app quits.
- Model selectors, thinking controls, login forms, and API-key entry.
- Steering, queued prompts, external extensions, and customization management.
- Remote access, pairing, independent daemons, and multiple concurrent sessions.
- Dedicated thinking, token-usage, and compaction displays.

## Runtime and module ownership

```text
Electron main -- owns startup/shutdown --> backend child process --> Pi SDK
      |                                         ^
      +-- native folder picker                  |
      +-- window lifetime             authenticated local HTTP/WebSocket
                                                |
                                         Svelte renderer
```

| Module                                  | Owns                                                                                                                 | Must not own                                                                |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `packages/desktop`                      | Windows, native folder selection, child-process supervision, connection credentials, current project/session locator | Agent execution, transcripts, application RPC forwarding                    |
| `packages/api`                          | Browser-safe Effect Schema definitions and Effect RPC contracts                                                      | Electron, Pi SDK, filesystem access, runtime services                       |
| `packages/server`                       | Current session, prompt acceptance, run lifetime, snapshots, subscriptions, HTTP/WebSocket listener                  | Window state, browser drafts, duplicate transcript storage                  |
| Pi integration inside `packages/server` | SDK creation, saved-session opening, Pi event translation, cancellation and disposal                                 | A generic multi-provider framework or independent application state machine |
| `packages/web`                          | Rendering, editable draft, connection status, native-capability calls                                                | Pi SDK, filesystem access, authoritative run state                          |

Use one backend composition root to construct the Pi integration and listener.
Electron has its own entry point for native startup and shutdown. Keep one-use
logic local and export only the interfaces callers need.

Use Effect for effectful backend logic, typed errors, and resource ownership.
Framework UI remains ordinary Svelte/TypeScript. Use Effect RPC with Effect Schema,
not oRPC, for this milestone. The web and server packages depend on `api`; the web
package must not import server implementations.

Electron starts and stops the backend child. The child exposes a loopback-only
HTTP/WebSocket endpoint with a per-launch credential. Reject unauthenticated
requests and unapproved browser origins. The preload bridge exposes narrow native
capabilities and connection details, never raw Electron IPC or Node access.

The backend session owns a run independently of any RPC call or subscription.
Closing a window, disconnecting a socket, or disposing a UI subscription must not
cancel accepted Pi work.

## Pi profile and data ownership

Embed and pin the current stable Pi SDK when implementation begins. Do not depend
on whichever global `pi` executable happens to be installed. The research baseline
was `@earendil-works/pi-coding-agent@0.85.1`; verify behavior against the version
actually pinned in the lockfile.

- Reuse the user's existing Pi credentials. Never copy credentials into pidex
  storage or expose them to the renderer.
- Use Pi's configured default model and normal fallback resolution. Display the
  resolved model. If no usable credentials/model exist, show setup instructions.
- Keep stock `read`, `bash`, `edit`, and `write` tools, automatic retry, and
  compaction. The selected folder is the working directory, not a sandbox.
- Honor project instructions such as `AGENTS.md` and `CLAUDE.md` through Pi's
  normal context-file mechanism.
- Disable external extensions, skills, prompt templates, themes, custom system
  prompts, and package-driven resource loading. Preserve credentials and model
  preferences separately; do not clear user configuration files.
- Keep Pi's persistent session manager. Do not use an in-memory session manager
  for normal application operation.

Pi JSONL files are the transcript source of truth. The backend derives the live UI
snapshot from the Pi session. Electron retains the exact session-file locator in
memory so a replacement backend can reopen it. No SQLite database or durable
pidex session index is required.

Saved history survives a backend crash, but unfinished output may not. Pi saves
completed messages rather than every streamed token. A crash before the first
assistant message is finalized can leave no saved file. Reopening history does
not resume interrupted work or undo tool side effects.

## Commands, subscriptions, and state

Keep the application interface focused on three capabilities. Exact identifiers
can follow the chosen SDK version without changing these semantics.

| Capability            | Contract                                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Send prompt           | Validate nonempty input, atomically accept only while idle, return acceptance separately from eventual run completion                        |
| Stop current run      | Target the observed run, begin cancellation, and acknowledge completion only when Pi has stopped; repeated stops must not affect a later run |
| Watch current session | Deliver a current snapshot, then ordered updates; reconnect restores current state without replaying commands                                |

The snapshot identifies the session and active run and includes the resolved
model, visible messages/tool activity, run status, and actionable failure details.
Subscription setup must not lose events between its initial snapshot and live
updates. The backend owns synchronization; the UI must not reconstruct missing
state by resending prompts.

Run status is `idle`, `running`, or `stopping`. A failed/completed/cancelled run
returns to idle with its outcome retained for display. Connection failure is a
separate UI state and disables submission until state is synchronized again.

- While running or stopping, keep the draft editable and disable Send. The backend
  must reject concurrent submissions even if the UI bypasses that control.
- Never automatically retry a send after a transport failure. Reconnect and
  reconcile against the snapshot; show unresolved acceptance explicitly rather
  than silently repeating work.
- Stop preserves the conversation and available partial output. Show `Stopping…`
  until cancellation finishes, then permit the next prompt in the same session.
- Surface expected failures as typed API errors. Distinguish invalid input, busy
  state, missing model/authentication, unavailable backend, and Pi run failure.
- Keep protocol/schema details out of ordinary user-facing errors. Include useful
  diagnostic context in logs without credentials or full prompt/transcript dumps.

## Desktop lifecycle and recovery

| User action or event                   | Required behavior                                                                                                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Launch app                             | Open the folder picker. Canceling leaves a usable project-selection screen and starts no Pi work. A valid selection creates a fresh session.             |
| Close window                           | Leave Electron and the backend running, whether Pi is idle or busy.                                                                                      |
| Reopen from Dock                       | Restore the window and synchronize with the same live session.                                                                                           |
| Quit while idle                        | Dispose the session, stop the child, and exit.                                                                                                           |
| Quit while running/stopping            | Ask whether to stop the run and quit. Cancel leaves the app/run unchanged. Confirm waits for cancellation and shuts down.                                |
| Backend exits unexpectedly             | Show an unavailable/error state and a Restart action. Do not automatically restart or resend work.                                                       |
| Select Restart                         | Reopen the exact saved session in a replacement child. Report any interrupted run. If no saved file exists, explain the missing history and start fresh. |
| Saved file exists but cannot be opened | Report the error; do not silently substitute another session or overwrite the file.                                                                      |
| Quit and relaunch the whole app        | Ask for a project and create a new conversation. Existing Pi history remains on disk.                                                                    |

Remembering the session locator across a backend restart is distinct from
remembering it across a full app restart. Do not select an arbitrary "most recent"
session on recovery; another Pi client may have created one in the same project.

A backend crash can leave already-executed filesystem changes. Recovery must never
claim those effects were rolled back or that interrupted work finished successfully.

## Use-case acceptance tests

Organize tests by user workflow, not private helpers. Each case must document its
starting state, action, observable result, and exact reproduction command. Use the
case IDs in test names so failures are easy to locate and rerun.

| ID    | Starting state and action                                                                                  | Observable result                                                                                               | Verification                                     |
| ----- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| UC-01 | Launch Electron; cancel the picker, then choose a temporary project                                        | Selection remains usable; valid choice connects to a fresh session and displays the model                       | Electron smoke + native checklist                |
| UC-02 | Idle session; send a prompt with controlled text and tool responses                                        | Text streams in order; tool inputs/results appear; exactly one run finishes and returns to idle                 | Backend/API integration + real-Pi checklist      |
| UC-03 | Hold a run active; submit another prompt directly through the API                                          | Typed busy rejection; first run continues; no second Pi invocation                                              | Backend/API integration; UI draft check manually |
| UC-04 | Active response/tool; request Stop, repeat it, then send after cancellation                                | Stopping is visible; next send waits for idle; same history remains; a stale stop cannot cancel the next run    | Backend/API integration + native checklist       |
| UC-05 | Accepted run; drop its client connection, including before the acceptance response arrives, then reconnect | Pi continues; snapshot restores current state; no prompt is resent or executed twice                            | Real transport integration                       |
| UC-06 | Active run; close the window, then reopen from Dock                                                        | Same run/session remains; current text/tool state reappears                                                     | Native checklist                                 |
| UC-07 | Saved session and active run; terminate the backend and select Restart                                     | Explicit unavailable state; exact saved history reopens; interrupted work is reported and not repeated          | Child-process integration + native checklist     |
| UC-08 | Crash before a first saved session exists; also exercise an unreadable saved file                          | Missing file is explained before a fresh session; unreadable existing file reports an error without replacement | Recovery integration                             |

### Deterministic automation

Use real HTTP/WebSocket handlers and clients, temporary project/session directories,
and controlled model responses. Exercise the real Pi SDK for its integration
contract where practical. Keep controlled dependencies at the provider/Pi seam;
do not mock the application behavior the test is meant to prove.

Control progress with explicit synchronization rather than arbitrary sleeps. Every
test cleans up sockets, sessions, child processes, and temporary files. Tests must
not use personal Pi credentials or read/write personal session directories.

The Electron smoke test runs on macOS and checks actual app launch, selection, and
backend connection with controlled responses. Full automated Electron coverage is
deferred; the native checklist remains a release requirement.

### Commands and manual reproduction

The following are required command interfaces for the implementation. They are
not all available in the current skeleton.

| Command                         | Required behavior                                                        |
| ------------------------------- | ------------------------------------------------------------------------ |
| `pnpm dev`                      | Launch the macOS Electron development app and its owned backend          |
| `pnpm test`                     | Run deterministic backend/API/Pi integration cases without paid requests |
| `pnpm exec vitest run -t UC-05` | Rerun a named acceptance case                                            |
| `pnpm test:desktop`             | Run the deterministic macOS Electron smoke test                          |
| `pnpm check`                    | Check formatting, lint, and types                                        |
| `pnpm build`                    | Build contracts, backend, web, and desktop entry points                  |

Before release, document exact fixture setup and launch commands for native
UC-01/04/06/07/09/10/13 reproduction. Include how to identify and terminate only
the app-owned backend for UC-07, along with the expected log location. These
commands must be executable instructions, not a request to edit private state.

For a real-Pi check, use a disposable project and a working Pi login, run
`pnpm dev`, and choose that folder. Ask Pi to create and read a small file, verify
the displayed tool results against the actual file, then exercise Stop and window
reopening during a longer run. Record the exact prompts, resolved model, versions,
and outcomes. Real model requests are explicit and never part of CI.

Bug reports include the use-case ID, commit and dependency versions, starting
state, reproduction command/actions, expected/actual results, and relevant
redacted logs. Add a failing regression scenario before fixing a reproducible bug.

## Release gate

v0.0.1 is complete when all acceptance cases pass through their specified
verification paths. Linux CI runs lint, deterministic tests, and build. macOS
verification runs the Electron smoke test and native checklist. Formatting and
type checks must also pass, and the real-Pi checklist must have a recorded result.

Remove Vitest's `passWithNoTests` exemption once behavior tests exist. A green empty
suite does not satisfy this release gate. Installer production and remote access
are not release requirements for v0.0.1.
