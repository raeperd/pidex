# Pidex v0.0.1: Desktop Pi workflow

Implementation target, not implemented.

## Problem statement

Pidex needs a usable Pi desktop client with clear module ownership and reproducible use-case tests. The repository currently contains only a skeleton.

## Solution

Launch Electron on macOS, choose one project, and use one Pi conversation. Show streamed Markdown, collapsible tool inputs/results, model name, and status. Pi owns history; closing the window keeps work running.

## User stories and acceptance scenarios

Each row pairs one user story with one acceptance scenario. Use the same UC ID in its test name; edge-case variants stay under that ID.

| ID    | User story                                                                                                | Acceptance scenario                                                                                                                                           |
| ----- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| UC-06 | As a developer, I want to close and reopen the window, so work can continue in the background.            | Close the window during work, reactivate the app; see the same live session and current output.                                                               |

## Implementation decisions

| Module                        | Owns                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| Desktop                       | Windows, folder picker, backend child lifetime, connection credentials, current session locator |
| API                           | Browser-safe Effect Schema and Effect RPC definitions                                           |
| Backend                       | Session/run ownership, prompt acceptance, cancellation, snapshots and subscriptions             |
| Pi integration inside backend | SDK setup, persistence, events and cleanup                                                      |
| Web                           | Rendering, drafts and connection status                                                         |

- **Transport:** Electron owns a loopback HTTP/WebSocket backend child. Use Effect RPC + Schema, Effect backend logic, and ordinary Svelte UI code. Web imports shared API definitions, never backend code. Require a per-launch credential and approved origins; preload exposes narrow native capabilities. Keep composition at process entry points.
- **Pi:** Pin the latest stable SDK at implementation. Reuse credentials, default model resolution, stock tools, retry, compaction, and project instructions. Disable external extensions, skills, templates, themes, custom system prompts, and package resource loading without modifying user configuration.
- **History:** Pi JSONL files are authoritative; no pidex database. Electron retains the exact session locator for backend recovery. Unfinished output may be absent; the first turn may have no saved file. Cancellation does not undo file changes.
- **API:** Send atomically accepts nonempty input while idle. Stop targets a run and waits for cancellation. Watch sends a snapshot then ordered updates without a gap. Backend-owned runs survive client disconnects. Never automatically resend prompts; reconnect reconciles state and exposes uncertain acceptance.
- **State:** Idle → running → stopping/idle. Failures return to idle with an actionable typed error. Busy/disconnected UI keeps drafts editable but disables Send; the backend independently rejects busy submissions. Credentials never reach the renderer or logs. Keep the project fixed until app exit.

## Testing decisions

Use Playwright's Electron support for programmatic application tests on macOS. Launch the real Electron app, preload, backend child, transport, and Pi SDK with temporary project/session storage. Drive the UI and assert visible results, saved files, and process lifetime. Control only model responses, native dialog results, and network/process failures; do not replace application handlers or set UI state directly.

UC-01–11 and UC-13 run through Electron UI/lifecycle integration. UC-12 uses an unauthorized client against that same running application because rejection has no legitimate UI action. Supporting integration checks, such as bypassing the disabled Send button or submitting a stale Stop, retain the owning UC ID; they do not substitute for its application scenario.

Playwright can access renderer windows and the Electron main process, but does not operate native OS dialogs. Supply folder-picker and confirmation results at the native-dialog boundary before invocation; exercise the real application response. Automate window close, app activation, Quit, and child termination through Electron/process controls. Keep a small manual macOS check for actual native dialogs and Dock behavior.

Each scenario needs starting conditions, actions, expected results, and an exact rerun command. Use explicit synchronization, isolate credentials/history, and clean up all processes and files. Capture Playwright traces, screenshots, and redacted application logs on failure. Playwright's Electron support is experimental; pin compatible Electron/Playwright versions.

**Done:** CI passes lint, formatting, types, build, and the mapped automated application scenarios on macOS. The real-Pi check explicitly covers file creation/reading, Stop, and window reopening in a disposable project. No paid requests in CI. Manual checks supplement the automated scenarios.

Implementation must supply launch and per-UC rerun commands, fixture setup, and artifact locations. Remove the empty-test exemption when tests exist. Bug reports use the UC ID, versions, reproduction steps, expected/actual results, and failure artifacts; fixes add regression coverage under the same story.

## Out of scope

- Installers/signing, Windows/Linux desktop acceptance, and remote access.
- History/project lists, project switching, last-session restore after full app exit, multiple sessions, automatic backend restart, and independent daemons.
- Model/thinking controls, login UI, external customization, steering/queues, dedicated thinking/token/compaction displays.
