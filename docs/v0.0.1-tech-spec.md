# Pidex v0.0.1: Desktop Pi workflow

Completed v0.0.1 baseline; retained as the acceptance and regression reference. Terms follow the [Pidex glossary](glossary.md).

## Problem statement

v0.0.1 established a usable Pi desktop client with clear module ownership and reproducible use-case tests. This document records the delivered scope that later releases retain unless explicitly superseded.

## Solution

Launch Electron on macOS, choose one project, and use one Pidex session backed by one native Pi session. Show streamed Markdown, collapsible tool inputs/results, model name, and status. Pi owns history; closing the window keeps work running.

## Implementation decisions

The application has three main processes: Electron main, the Svelte renderer, and one server child. The Pi SDK runs inside the server child. API definitions are shared code, not a process. Electron and Pi tools may also create supporting subprocesses.

| Module  | Runs in           | Owns                                                                                                               |
| ------- | ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| Desktop | Electron main     | Windows, folder picker, server child lifetime, connection credentials, current session locator                     |
| API     | Shared code       | Browser-safe Effect Schema and Effect RPC definitions                                                              |
| Server  | Server child      | Embedded Pi SDK, session persistence, run lifetime, prompt acceptance, cancellation, events, snapshots and cleanup |
| Web     | Electron renderer | Rendering, composer drafts and connection status                                                                   |

- **Transport:** Electron owns a loopback HTTP/WebSocket server child. Use Effect RPC + Schema, Effect server logic, and ordinary Svelte UI code. Web imports shared API definitions, never server code. Require a per-launch credential and approved origins; preload exposes narrow native capabilities. Keep composition at process entry points.
- **Pi:** v0.0.1 pinned Pi SDK 0.85.1 and reused credentials, default model resolution, stock tools, retry, compaction, and context files. It disabled external extensions, skills, templates, themes, custom system prompts, and package resource loading without modifying user configuration.
- **History:** Pi JSONL files are authoritative; no pidex database. Electron retains the exact session locator for server recovery. Unfinished output may be absent; a new session may have no saved file yet. Cancellation does not undo file changes.
- **API:** Send atomically accepts nonempty input while idle. Stop targets a run and waits for cancellation. Subscribe sends a snapshot then ordered updates without a gap. Server-owned runs survive client disconnects. Never automatically resend prompts; reconnect reconciles state and exposes uncertain acceptance.
- **State:** Idle → running → stopping/idle. Failures return to idle with an actionable typed error. Busy/disconnected UI keeps composer drafts editable but disables Send; the server independently rejects busy submissions. Credentials never reach the renderer or logs. Keep the project fixed until app exit.

## Testing decisions

### Coverage

- Use Playwright Electron on macOS. Support is experimental; pin compatible versions.
- If Playwright Electron lacks a required testing capability, consider WebdriverIO with `@wdio/electron-service`.
- Run all scenarios except [#140](https://github.com/raeperd/pidex/issues/140) through the Electron UI and lifecycle.
- Run [#140](https://github.com/raeperd/pidex/issues/140) against the full app using an unauthorized client.
- Keep supporting integration checks under the same issue number; they supplement application scenarios.
- Assert visible results, saved files, and process lifetime.

### Test setup and debugging

- Run the real Electron app, preload, server, transport, and Pi SDK.
- Control only model responses, native dialog results, and network/process failures. Keep application handlers and UI state real.
- Supply native dialog results before invocation; automate window close, activation, Quit, and child termination.
- Use temporary projects, sessions, and credentials. Synchronize explicitly and clean up processes/files.
- Give each scenario starting conditions, actions, expected results, and an exact rerun command.
- Provide launch, per-issue rerun, and visible step-through commands, fixture setup, and artifact locations.
- Save traces, screenshots, and redacted logs on failure. Bug reports include issue number, versions, steps, and expected/actual results.

### Release checks

- Pass all 13 automated scenarios, lint, formatting, types, and build in macOS CI.
- Manually check native dialogs and Dock behavior; these checks supplement automation.
- Record a real-Pi run in a disposable project: create/read a file, Stop, and reopen the window.
- Keep paid requests out of CI. Remove the empty-test exemption when tests exist.

## Implementation workflow

1. Choose a use case; add shared setup only as needed.
2. Write its application test and observe the expected failure.
3. Implement the smallest change that passes.
4. Refactor with tests green.
5. Watch the Electron scenario and record verification results.

- Each PR names its issue numbers and verification results.
- Related cases may share a PR; there is no fixed PR count.
- Bug fixes add regression coverage under the owning issue number.
- Release v0.0.1 when every release check passes.

## Out of scope

- Installers/signing, Windows/Linux desktop acceptance, and remote access.
- History/project lists, project switching, last-session restore after full app exit, multiple sessions, automatic server restart, and independent daemons.
- Model/thinking controls, login UI, external customization, steering/queues, dedicated thinking/token/compaction displays.
- File-tree panels, browser tabs, and integrated terminals.
