Choose a model and thinking level inside Pidex, recover from model setup failures, and retain those choices when returning to a session. Proposed for `raeperd/pidex` v0.0.3 after [v0.0.2](https://github.com/raeperd/pidex/milestone/2). This is a local draft; no v0.0.3 milestone or issues have been published. Terms follow the [Pidex glossary](https://github.com/raeperd/pidex/blob/main/docs/glossary.md).

## Problem

The current API exposes a model display name but no model or thinking controls. An unresolved Pi default directs the user to change Pi settings and restart Pidex. v0.0.2 plans project, session, and composer-draft continuity, but remains open. Users need to choose a usable model while keeping the session and unsent work they are trying to continue.

## Intended outcome

Choose a model for the selected idle session, set a supported thinking level, and see the confirmed effective settings before sending. Restore those settings across navigation and relaunch, including a session that has never sent a prompt. Keep one active Pi session and one run in progress. Complete this composer workflow before adding cross-session preferences or more provider configuration.

## Use cases and acceptance scenarios

Local IDs define proposed issue boundaries. Each row owns one Electron application scenario; its failure variants stay under that case. Across all scenarios, discovery, setting changes, Retry, restoration, and setup recovery make no inference requests, preserve composer drafts, and leave global/project defaults unchanged. Only explicit Send starts a run.

| Local ID | Outcome | Acceptance scenario and variants |
| --- | --- | --- |
| M03-A | Find a usable model | Open a project with two configured providers and models with colliding display names. Search by provider, name, or model ID and navigate choices by keyboard. Distinguish loading, no matches, no authenticated choices, and discovery failure. Keep a missing current choice visible as unavailable. A failed provider lookup leaves healthy choices usable; Retry refreshes discovery without changing selection. |
| M03-B | Change the session's model | With saved history and an unsent composer draft, select another model while idle. After confirmation, explicitly Send and verify the selected provider/model receives earlier context in the same Pi session. Reject invalid, unauthenticated, busy, and stale-target requests before mutation. Reconcile a dropped response. A write failure shows the actual effective state and an unsaved error, and blocks Send until recovery. |
| M03-C | Choose a supported thinking level | Select a supported level, then switch to models with restricted thinking and no thinking support. Show Pi's effective model, level, and supported choices together. Cover per-model defaults, capability clamping, and a stale request for the previous model. Explicitly Send and verify the effective thinking behavior in the provider request. Switch back to a thinking model and verify its controls recover. |
| M03-D | Recover from an unresolved default | Launch with an invalid Pi default and an authenticated alternative. Open the picker, choose the alternative, and explicitly send the retained draft without restarting. Cover missing credentials, failed selection, and discovery Retry. After successful selection, validate the effective session model instead of continuing to reject the startup default. |
| M03-E | Restore each session's choices | Give two saved sessions different model/thinking settings. Change settings without sending again, then switch, close/reactivate, and quit/relaunch. Restore each session's settings and draft. Repeat before a session's first prompt, including an empty composer; after a successful reply, verify handoff to Pi history. Cover metadata write failure, interrupted handoff, explicit server recovery with saved history, and an unavailable saved model requiring explicit replacement. New session uses Pi defaults. |

## Implementation decisions

These are proposed Pidex behaviors based on the Pi version noted under References.

### Discovery and setup recovery

- Use Pi's model catalog and credential resolver. Identify a model by provider and model ID, with a display name for readability. Preserve support for AWS credential chains and Vertex ADC; API-key presence alone is not an availability check.
- Offer choices with configured authentication and retain the current or restored unavailable choice with a reason. Configured authentication does not guarantee a successful inference request. Keep keyboard focus predictable, support Escape, and return focus to the composer after selection.
- Use local and cached catalogs with network catalog refresh disabled. Bound asynchronous discovery/auth checks, separate provider failures from empty results, and provide Retry. Auth resolution may perform network work.
- Refresh never changes the selection. Ignore responses targeting an earlier project/session. The picker remains accessible when setup blocks Send, so choosing a valid model can resolve an invalid startup default.

### Mutations and thinking

- Apply an idle model change immediately through Pi's session setter. A choice becomes confirmed only after the server reads back its effective state and completes the required persistence work. Keep the existing session history.
- Serialize setting mutations with Send, New session, Resume, and project switching. Reject changes during Running or Stopping at the API. Carry the target project/session identity and expected model identity for thinking changes. Keep Send disabled during mutation or reconciliation, including after reconnect.
- Return provider/model identity, effective thinking, supported thinking choices, setup status, and persistence status together. Pi applies a per-model thinking default, then a global default, then the current level on model switch, and clamps to capabilities. Use Pi's read-back result rather than preserving a stale UI value.
- Derive supported levels from Pi. Hide the interactive thinking control when unsupported and expose effective Off in session state. Reject unsupported direct thinking requests before mutation.
- Preflight validation/auth failures leave the prior state usable. A failure after mutation begins may leave memory changed or only part of the settings written. Report the effective and unsaved state and block Send until reconciliation verifies persistence. A snapshot of memory alone does not prove a failed write recovered. Do not retry a no-op setter and assume it rewrote the missing history entry.
- Reconnect retrieves an authoritative snapshot before further changes or Send. A dropped response or failed read-back remains unresolved until reconciliation.

### Persistence and restoration

- Pi history owns saved-session model and thinking settings, including edits followed by Quit without another prompt. Preserve exact saved-session identity and use Pi's APIs for history changes.
- Pi defers a new session file until an assistant message exists. Extend v0.0.2's session-draft metadata only for this gap, recording provider/model and effective thinking beside the composer draft. A settings-only session draft remains restorable with empty composer text. A session-file path by itself is not proof that settings are on disk.
- Restore draft settings through the server, validate availability, and publish effective state. Flush them before ordinary navigation, window close, and Quit under v0.0.2's write-failure policy. Keep unsaved state recoverable and require explicit discard before leaving it after a failed write.
- Remove the temporary settings override only after Pi history durably contains the effective choice. Retain it if handoff fails. On restoration, validated durable Pi history takes precedence over leftover draft settings; stale metadata must not overwrite a later choice. Cover an interruption between saving history and removing metadata.
- Inspect the requested saved model and Pi's restoration result. Pi can fall back when the model is missing or lacks configured authentication. Keep the requested identity visible as unavailable and Send disabled until the user explicitly chooses a replacement. Do not report Pi's fallback as a successful restoration of the requested choice.
- New session resolves Pi's configured defaults.

## Testing decisions

- Test all five workflows through Playwright Electron on macOS with real preload, authenticated transport, server, Pi SDK, and filesystem persistence. API checks for stale targets, races, and typed failures supplement the application scenarios.
- Isolate project directories, Electron user data, Pi configuration, credentials, session files, and metadata. Extend the existing local-provider fixture with distinct providers and thinking capabilities. Control provider responses, native dialogs, auth/network failures, and process failures at external boundaries. Exercise real session and metadata files for persistence failures.
- Assert actual provider/model routing, earlier context, effective thinking, session identity, and the shared scenario rules. Include a model change followed by reload before another prompt, so stale thinking cannot hide behind a later successful run. Preserve existing v0.0.1/v0.0.2 regression coverage.
- Use local IDs in test names until issue publication. After tests exist, rerun a case with `pnpm test --grep 'M03-C'`; step through visibly with `pnpm build && pnpm exec playwright test --grep 'M03-C' --debug`. Record fixture setup, versions, reproduction steps, and expected/actual results. Save traces, screenshots, and redacted logs under `test-results/` using the existing fixture and CI artifact conventions.
- Release after v0.0.2 completes and every scenario and failure variant passes. Require `pnpm check` and `pnpm test`, matching macOS CI's check, build, and Playwright steps. Record a real-Pi smoke run across two providers, thinking changes, settings-only relaunch, and an unsent session draft. Keep paid inference outside CI.

## Implementation workflow

M03-A → M03-B → M03-C → M03-E. M03-D follows M03-B and can run in parallel with M03-C and M03-E. All five must complete before release.

M03-A establishes catalog identities and discovery states. M03-B establishes session mutation, confirmation, and failure semantics; it must already read back thinking after a model change. M03-C adds explicit thinking controls and capability coverage. M03-D reuses selection to clear setup errors. M03-E depends on M03-C and v0.0.2's stable session identities, navigation, and durable draft lifecycle. Coordinate edits to the shared API and server snapshot/setup logic across M03-C and M03-D; M03-E also coordinates with Desktop's metadata owner.

- Implement one scenario at a time: observe a behavioral test failure, make the smallest change that passes, then refactor while green. Retain completed scenarios as regression coverage and record visible verification.
- Link each PR to its issue and the eventual v0.0.3 milestone. Complete required checks and repository review. Readiness depends on acceptance coverage, not a fixed PR count.

## Out of scope

Carry forward [v0.0.2's exclusions](https://github.com/raeperd/pidex/milestone/2), with model/thinking controls brought into scope here. Also exclude:

- Provider installation, catalog editing, network catalog refresh, and global/project default editing. Login and credential entry remain in Pi.
- Sticky cross-session preferences, favorites, profiles, fast-mode controls, multi-model dispatch, and a general provider-options framework.

## References and open decisions

### Evidence that changes the plan

Pidex's [dependency][pidex-package] pins Pi 0.85.1. The package was not installed in this worktree, so API claims use the matching release source. Recheck the installed package during implementation; no SDK upgrade is proposed. Upstream tests cited below were inspected, not executed.

| Evidence | Consequence for Pidex |
| --- | --- |
| Pi 0.85.1 [SDK catalog/auth documentation][pi-sdk] and [ModelRuntime APIs][pi-models] support local catalogs, provider availability, and bounded auth operations. | Reuse Pi discovery and credential resolution. |
| Pi [session setters][pi-setters] update state and append history; [tests][pi-tests] cover session-only defaults, per-model thinking, and clamping. | Confirm effective model and thinking together after each change. |
| Pi [session persistence][pi-persistence] delays the first file until an assistant message and appends to memory before writing. [Restoration][pi-restore] can choose a fallback. | Add the narrow session-draft settings record, detect partial writes, and require explicit replacement of unavailable saved models. |
| t3code's [picker][t3-picker] uses provider-scoped choices; [catalog tests][t3-catalog-tests] retain missing selections for dynamic providers and replace unavailable markers after recovery. [Selection][t3-selection] records composer intent. | Show provider/model identity and preserve unavailable choices. Pidex's proposal applies the choice immediately to its single active Pi session. |
| Paseo's [catalog API][paseo-catalog] and [model browser][paseo-browser] separate provider errors, loading, and empty results. | Keep Retry distinct from selection and retain healthy provider choices during partial discovery failure. No exact invalid-Pi-default recovery test was established in the inspected paths. |
| Paseo's [Pi adapter][paseo-pi] reads state after setters; [adapter tests][paseo-pi-tests] cover refreshed thinking and failed read-back. Its [manager regression][paseo-persistence] saves the resolved thinking and provider handle before another turn using a test provider. | Test settings-only reload and read-back failure in the real Pidex Electron/Pi boundary. Paseo's daemon persistence is not a replacement for Pi-owned history. |

The current [setup guard][pidex-setup] checks the configured default before the effective session model, which explains M03-D.

### Decisions to settle before implementation

- The proposed scope includes retaining model/thinking settings before the first reply. Accepting M03-E also accepts that narrow extension to v0.0.2's metadata store.
- The proposed New session behavior uses Pi defaults. Remembering another session's last selection would be additional scope.
